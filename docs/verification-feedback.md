# 验证失败后的证据反馈闭环

在 run/chat 会话中，修复后的验证命令非零退出、超时或无法启动时，控制器会保存失败输出，关联这次修改及上次诊断，并在预算内发起新的只读调查。新的修改仍需要明确的修复任务。

## 离线演示

```bash
conda activate researchcoder
cd /home/example/ResearchCoder
python -m corecoder.feedback_demo --output-dir .tmp/feedback-demo-new
```

输出目录须不存在。演示先做一次错误的常量补偿修改，原断言实际失败；系统采集输出并重新读取源码，生成新诊断。随后第二条明确任务移除补偿、改用浮点除法，再执行原断言通过。

模型决定由脚本固定，文件修改、失败输出、源码读取和命令复验实际执行；此演示不代表模型效果测评。

## 实际会话

```bash
researchcoder chat --project /path/to/project --log /path/to/failure.log \
  --max-feedback-rounds 2 --verify python -m pytest tests/test_related.py -q
```

先要求诊断，再明确要求修复。若验证失败：

1. 这次修复继续标为 `verification_failed`；验证命令无法启动时保留 `incomplete`，不伪造应用退出码。
2. 输出被保存为新的 `verification.log`，提取新证据并关联本次修复、先前报告和已修改文件的哈希。
3. 自动发起只读调查，读取当前代码，重新审视先前假设，区分原问题、剩余问题、新问题和验证环境问题。
4. 通过结构及引用校验的新报告可供解读或修复。输入 `/review 解释新的失败` 或 `/repair 修复新诊断发现的问题`；控制器不会自行开始第二次修改。

`--max-feedback-rounds` 默认 2，可设为 0–5；0 仍保存失败输出，但不自动调用诊断模型。同一会话的反馈调查计数不因新一轮任务重置，失败的模型构造、API 请求和显式重查当前反馈也消耗次数。预算耗尽后保留输出及原因，停止后续反馈模型调用；需要新的调查时显式开始新会话。

## 关联和上下文

一次失败通常保存以下文件：

```text
session.json
turn-002-repair.json
turn-002-feedback/
  verification.log
  feedback.json
turn-002-feedback-diagnosis.json
```

- `repair.json` 保留实际验证状态及修改记录。模型声称“已修复”不能改变验证结果。
- `feedback.json` 保存稳定反馈 ID、修复记录及原报告的路径与哈希、验证参数数组、退出码或超时状态、保留的 stdout/stderr、旧假设摘要、修改前后哈希。
- 新报告的 `feedback_context` 保留有界摘要及祖先引用，避免递归复制全部历史报告；下一次修复交接继续携带这些数据。
- 修改过的 Python 文件和先前已观察源码作为读取提示，不包含期望答案。新的文件观察来自当前磁盘，而非沿用修改前源码。
- 反馈日志和修复记录在重新调查前核对哈希；发生变动时拒绝将它们静默作为同一份反馈使用。旧记录保留供审计。
- 更换日志或绑定报告会清除活动反馈关联，历史反馈记录和已消耗次数保留。后续修复验证通过时清除活动失败上下文。

每个输出流保留最多 12000 个原始字符，较长输出保留头尾并标明原始长度和省略数量。超时保留当时已收集的输出，未获得退出码时明确标记不可用。stdout/stderr 分开保存，不声称恢复了两条流的完整时间顺序。当前验证执行仍沿用进程输出采集方式；这里限制的是落盘记录和诊断输入，并非流式执行内存上限。

反馈调查只开放现有五个只读证据工具，并沿用工具、轮次和上下文预算。反馈诊断不完整、API 异常或中断不会覆盖原修复结果，也不会使旧诊断重新成为活动修复报告。费用与调用统计分别保存在父修复和反馈调查中，累计时需要合并；这项功能可能增加调用量。

独立的 `researchcoder repair` 子命令仍输出修复记录；自动反馈调查由 run/chat 控制器负责。使用原子命令生成的失败记录，也可通过 `create_feedback` 导出日志，再绑定到新的诊断会话。

## 一次真实模型功能验收

```bash
python examples/feedback_live_acceptance.py --live \
  --output-dir .tmp/feedback-live-new --max-requests 20
```

该命令使用已配置的 API，创建独立的小型 metrics 项目，包含均值除法和缩放计算两个受控故障。首轮任务明确只修复均值，保留缩放问题，让原校验脚本继续失败；控制器重新诊断后，第二条明确任务修复缩放。保留原校验脚本哈希并再次独立执行，核查测试未被改弱。

这是实际模型、工具和验证命令的集成验收，不是真实训练故障集，也不是独立任务的修复成功率基准。输出 `summary.json` 保留成功或不完整结果、请求尝试数和提供方用量，不静默丢弃失败。

脚本默认最多 20 次提供方请求尝试，每次关闭客户端与框架重试，300 秒后不再发起新请求（已在途请求仍受客户端超时控制）。未提供 `--live` 时不会调用 API；`--env-file` 可指定已有配置文件。`--direct` 仅在本次验收进程中忽略代理环境，不修改系统配置。

## 验证范围

```bash
python -m pytest tests/test_verification_feedback.py -q
python -m pytest tests/ -q
```

覆盖实际非零退出、超时输出、启动失败、截断与哈希、原报告关联、当前源码版本、反馈预算、模型失败、禁止自动再次修改和第二条明确任务的复验。判断“上次假设是否成立”仍由模型基于证据分析，程序只校验结构、引用和执行事实。
