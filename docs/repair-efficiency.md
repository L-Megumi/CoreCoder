# 修复阶段的证据复用与停止条件

上一轮真实验收暴露了两个问题：诊断已读到的配置和报错源码没有进入修复交接，模型再次调查；多个案例共享可被先到者耗尽的请求池，后续案例没有剩余预算。本阶段修改产品修复流程及验收预算管理，不追加付费模型请求，不改写上一轮的 2/6 独立检查结果。

## 交接已读取的源码

`load_handoff` 仍核对报告归属、结构、引用及当前文件 SHA-256，再提取最多六个源码片段。优先选择原因假设引用的当前观察及配置/文件读取；旧版本观察不作为当前片段。

片段包含观察 ID、路径、哈希、实际起止行和内容，只保留完整返回的行。单片段内容最多 1,400 字符，整个片段数组序列化后最多 10,000 字符；省略量和原始截断状态显式记录，完整观察留在诊断报告中。报错行位于片段中部时围绕该行选取，不只保留文件开头。

每次修复模型调用前重新核对这些片段的文件哈希。修改后失效的观察 ID 单独列出，旧交接只作为历史快照；需要新内容时读取当前文件。已覆盖且版本仍一致的片段可以直接用于核查与最小修改，不必先完整重读文件。框架不会将某条诊断假设自动当作正确答案。

## 重复读取与调查上限

- 相同绝对路径、offset、limit 和文件哈希的成功 `read_file` 结果可以复用；缺省参数与显式缺省值按同一请求处理。
- 每次仍先执行权限/范围检查并核对文件哈希。首读前后版本不一致时不建立缓存；外部修改后不复用旧内容。
- 写文件、编辑文件或命令执行会清空读取缓存。搜索目录可能发生新增/删除，因此本阶段不缓存 grep/glob 结果；命令和修改操作也不会被重复请求抑制。
- 复用结果引用原工具事件，长结果明确省略中段，需要完整中段时可读取更小行范围。缓存只减少重复工具执行和重复返回的长内容；哈希校验本身仍读取文件，不能据此宣称磁盘 I/O 降幅。

默认最多连续调查八轮。这里一轮指模型返回的一组工具调用；多工具并行返回仍算一轮。连续四轮没有实际文件改变时提醒复用已知事实、聚焦信息缺口；八轮后在下一次模型调用前停止，记录 `incomplete` 和 `investigation_limit`，不强迫模型编辑。

文件工具使文件哈希实际变化，或命令使已观察/已跟踪文件变化，才重置连续计数。重复写入相同内容不算进展。命令在跟踪范围之外的副作用不能作为已确认进展，原有总轮数及工具调用上限同时保留。复杂修复可调高连续调查上限：

```bash
researchcoder repair diagnosis.json --project /path/to/project \
  --instruction '修复诊断指出的问题，保留原校验' --output repair-new.json \
  --max-investigation-rounds 12 --verify python check.py

researchcoder chat --project /path/to/project --max-investigation-rounds 12
```

Python 接口 `run_repair`、`RepairAgent`、`RoutedSession` 同样支持 `max_investigation_rounds`，范围为 1 到 30。通用 code 模式保留原循环、七个工具和原上下文管理。

## 不调用模型的修复上下文压缩

修复阶段单独使用确定性上下文管理器，保留最初的明确任务与交接，再按完整工具调用组保留最近历史。并行工具请求与其响应一起保留或一起省略，不产生孤立 tool 消息。

已核对的源码记忆和调查计数每轮重新加入请求；省略旧历史时说明内容可从审计恢复，不伪造模型摘要。任务、源码记忆及工具声明无法放入估计预算时明确中止。Token 数仍是字符估计，不能代替提供方账单。完整工具结果保留在修复审计中；产品原通用编程上下文不受影响。

## 修复中断与独立验证分开

若循环因轮数、连续调查或提供方错误中断，但确实写入过文件变化，并已指定验证命令，控制器仍执行该命令，标记 `verification.trigger=partial_file_changes`。检查通过时，原 `status=incomplete` 及错误原因继续保留，不提升为 verified。

`workflow_completed` 表示模型修复循环是否正常结束；实际执行结果以 `verification` 为准。模型正常结束且指定命令退出零时才得到 `status=verified`。用户主动中断时不再启动验证；没有文件变化的中断也不会额外执行命令。验证失败仍可按已有次数限制触发只读反馈调查。

## 案例预留预算

六案例运行器在任何请求发出前，先扣除所有历史阶段的请求尝试数，再按剩余容量平均预留各活动案例的新增配额。排序仅用于分配不足一轮的余数，后续执行顺序不会改变配额；早期案例不能借用后续案例的配额。

例如总上限 72、六个全新案例、每例累计上限 14，会各预留 12 次。按上一轮恢复前的 46 次历史记录和每例累计上限 20 计算，五个尚未修改案例可分别预留 6、5、5、5、5 次；这是预算算术回放，没有重新测试历史案例。

未用完的配额本轮不自动转移；总预算、每例累计预算、每例本阶段配额和时间限制共同生效。接口回退也计数，请求前保存 `request-ledger.json`。已有结果、阶段目录或预算计划时拒绝重跑该阶段，避免中断后静默重置计数。零配额的案例不构造模型客户端或发起请求，仍记录未完成及独立检查结果。

```bash
python -m pytest tests/test_repair_efficiency.py -q
python -m corecoder.repair_efficiency_demo --output-dir .tmp/repair-efficiency-new
```
