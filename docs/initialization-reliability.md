# 初始化证据核查与归因不确定性

## 解决的问题

stage16的拼接对照中，三个报告没有读取构造函数，却按常见库用法断言默认维度为1；当前源码实际上为0。另外一些报告虽然读到了0，仍直接断言调用方有错、库实现没有缺陷。既有结构和引用校验无法识别这些语义错误。

本阶段补充两个环节：调查清单要求实际读取初始化来源；诊断提示要求区分已读事实、报错机制、原因假设和责任归属。报告JSON结构和六个诊断工具保持兼容。

## 静态线索与实际观察

源码定位已在受限文件读取后解析AST。本阶段给普通实例方法的函数范围增加`initialization_check`：收集方法直接读取的接收者属性，在同一类唯一、未装饰的本地`__init__`中寻找对应赋值，返回签名及赋值语句的行号。默认表达式和项目代码都不会被执行。

该元数据不返回推断的默认值，不证明构造函数执行过，也不证明运行时绑定。只有实际可见源码行才算观察。启用`completion_mode=checklist`后，调查清单比对同一路径、同一SHA的当前片段；未覆盖签名或赋值语句就安排`read_project_file`，分段覆盖可以合并。文件新版本会使旧页失效。

实际读取后，工具结果附带`initialization_source_lines`，上下文投影和证据记忆保留这些带原始行号的源码行。长行仍明确标记省略，不能据此假定没有省略的参数。

## 预算与未知情况

- 每次方法/初始化体的附加分析最多访问4000个AST节点；达到限额明确未知。
- 线索展示最多12个实例属性、20行签名、32行必读源码位置；超过限额标注省略或未完整核查。
- 单次额外读取最多60行，沿用既有工具和模型轮次预算；不因为新增核查自动扩充额度。
- 继承、装饰器、无唯一初始化、动态属性等不推断运行值。超长不可读取行会标为blocked，避免重复请求。
- blocked表示未知。调查可带局限结束，并不表示属性不存在或初始化正确。

现有统一`run/chat`诊断工作流已启用调查清单。独立诊断CLI默认仍为`off`，需显式传入`--completion-mode checklist`才能强制完成本核查；提示中的事实与归因约束对两种模式都生效。

## 归因规则

“默认值为多少”应来自已实际读取的当前源码；未读取时必须待核实。看到输入与默认值不匹配，可以解释报错机制，但缺少接口契约、测试或版本比较时，不能据此确定责任在输入、配置还是实现。在原因假设中保留可行解释，在limitations说明需要核对的预期语义。

这部分是模型提示约束，不是自然语言结论的完整语义验证器。初始化源码覆盖通过，也不能保证根因正确；原有报告有效性指标含义不变。

## 回归与实测

新增37项测试（22项初始化、15项报告一致性）覆盖未读默认值、只读状态计算、分页覆盖、旧版本失效、多行语句、投影保留、继承与动态未知、重复初始化、多方法、嵌套函数、不同接收者名、位置参数、截断与分析限额、不执行默认表达式、拒绝核查时有界停止。

真实复核在stage16未修改的卷积、拼接、无堆栈NaN副本上，对tools和both配置各运行一次，共6次诊断，预设最多60次底层请求、每例每配置最多10次。不传标注、原始健康版本或人工案例提示，不做补跑或报告恢复，不执行修复。

初版6次诊断发现无关搜索候选会扩大检查范围，已限定为经核对的堆栈方法或已解析的方法定义，补充4次诊断回归。进一步发现两份报告有显式归因矛盾，增加中文词法一致性检查并用已有观察各纠正一次；三阶段累计46/60次请求。详见[完整记录](initialization-reliability-results.md)。

归因一致性检查沿用现有一次报告纠正预算，只检测部分中文明确矛盾，不是语义真值校验器。

该复核用于观察新增机制是否进入真实工具链，以及模型是否保留归因不确定性。不是新四组消融，不重新确认stage16的20%输入Token降幅。此前48次对照的原始记录和源码哈希单独保留。
